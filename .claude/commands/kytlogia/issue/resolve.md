argument-hint: <issue番号>

issue #$1 の対応を、役割の異なる2つのセッションを並行実行させることで自動化する。

2セッションは互いに直接メッセージを送り合わない。共有されているGitHub PRの状態(CIステータス・レビューコメント・レビュースレッドの解決状況)をそれぞれがポーリングして連携する。これにより、どちらかのセッションが待機中でも状態がGitHub側に残り、やり直しがきく。

## セッションIDとコメントの付記

- 自分自身(このコマンドを実行しているセッション)のスクラッチパスなど環境情報に含まれるセッションUUIDの先頭8桁を`token`とする。取得できない場合は `uuidgen | cut -c1-8` などで代わりに生成する。
- 作業セッションのIDは `$1-work-<token>`、レビューセッションのIDは `$1-review-<token>` とする(Agent起動時のdescriptionにもこれを使う)。
- 各セッションがPRに投稿するコメント(レビューコメント・返信など)には、末尾に必ず以下の形式でフッターを付ける。誰が/どのセッションが投稿したかをレビュアーが区別できるようにするため。
  - 作業セッション: ``_🤖 [Claude Code](https://claude.com/claude-code) · /kytlogia:issue:resolve 作業セッション (`$1-work-<token>`)_``
  - レビューセッション: ``_🤖 [Claude Code](https://claude.com/claude-code) · /kytlogia:issue:resolve レビューセッション (`$1-review-<token>`)_``
- レビュースレッドをresolveするだけの操作(新規コメントを伴わない)にはフッターは不要。

## 起動前チェック

- `gh issue view $1` でissueが存在しクローズされていないことを確認する。存在しない/クローズ済みならユーザーに報告してここで終了する。

## Agent起動

Agentツールで以下の2プロンプトを同じメッセージ内で並行して起動する(両方 `run_in_background: true`)。起動後はユーザーに「作業セッションとレビューセッションを起動した」旨を報告し、以降は完了通知を待つ(ポーリングでAgentの様子を伺わない)。

### セッション1(作業セッション、description: `$1-work-<token>`)

以下をそのままAgentへのプロンプトとして渡す:

> issue #$1 に対応する。
>
> 1. `gh issue view $1` の内容を確認し、実装する。作業ブランチを切り、実装し、コミットする。
> 2. `gh pr create` でPRを作成する。本文に `Closes #$1` を含め、issueとリンクさせる。
> 3. `gh pr checks <PR番号> --watch` でCIの完了を待つ。
> 4. (初回のみ)Copilotレビューの完了を待つ: `gh pr view <PR番号> --json reviews` などで `copilot-pull-request-reviewer` からのレビューが付くか、最大15分ポーリングする。15分経ってもレビューが付かない場合はquota制限でスキップされたとみなし、次に進む。
> 5. CIの失敗やCopilotレビューの指摘があれば内容を確認して修正・pushする。インラインレビューコメントに対応した場合は、対応内容を1行で要約したフッター付き返信を該当スレッドに投稿する(`gh api repos/{owner}/{repo}/pulls/{pull_number}/comments/{comment_id}/replies`。`{pull_number}`は省略不可)。修正後は3(CIの完了待ち)だけをやり直す。4(Copilotレビュー待ち)は初回のみで、以降のpushのたびに繰り返さない(pushごとに再レビューされるとは限らず、毎回15分待つと大幅に遅延するため)。指摘が無くなるまでこれを繰り返す。
> 6. ここまでの指摘が解消したら、別セッションによるレビューが付くのを待つ。PRのレビュースレッド(`gh api graphql`などでレビューコメント一覧を取得)を1〜2分間隔でポーリングし、新規のレビューコメントを待つ。自分自身が5・7で付けたフッター(`$1-work-<token>`)を含むコメントは新規指摘としてカウントしない(自分の返信を指摘と誤認して無限ループするのを防ぐため)。
> 7. レビュー指摘が付いたら内容を確認して修正・pushする。対応内容を要約したフッター付き返信を該当スレッドに投稿する。未解決のレビュースレッドが無くなるまで6〜7を繰り返す。
> 8. CIがグリーンで未解決のレビュースレッドも無い状態になったら、その旨をユーザーへの最終報告にまとめてセッションを終了する(マージは行わない)。このセッションはここで完了するため、後でユーザーが「マージして」と言った場合はユーザー自身か、この作業セッションを起動した親セッションが直接`gh pr merge`を実行すること。

### セッション2(レビューセッション、description: `$1-review-<token>`)

以下をそのままAgentへのプロンプトとして渡す:

> issue #$1 に対応するPRをレビューする。
>
> 1. issue #$1 を参照するPRが作成されるまで待つ(`gh pr list --search "\"Closes #$1\" in:body state:open"`などを1分間隔で、最大30分ポーリングし、本文に`Closes #$1` を含むPRを探す)。30分経っても見つからない場合、`Closes #$1`の表記ゆれ(改行・大文字小文字など)や検索クエリ自体の失敗を疑い、`gh pr list --search "$1 in:body state:open"`(issue番号のみ、誤爆の可能性はあるが候補として提示する用)でも探す。それでも見つからなければユーザーに報告してセッションを終了する。
> 2. PRが見つかったら、CIがグリーンになり(`gh pr checks <PR番号>`)、かつ直近数分間新規コミットが無い(CI修正やCopilotレビュー対応が落ち着いた)状態になるまで待つ。
> 3. `code-review` スキルでこのPRをレビューし、指摘があればインラインコメントとして投稿する(例: `/code-review <PR番号> --comment`)。各コメント本文の末尾にフッターを付ける。
> 4. 指摘に対する修正コミットがpushされるのを待ち(`gh pr view <PR番号> --json commits` などをポーリング)、該当箇所を確認する。
> 5. 修正が妥当なら、そのレビュースレッドを解決する(`gh api graphql` の `resolveReviewThread` mutationを使う。新規コメントや返信は不要)。まだ問題があれば追加でコメントする。
> 6. 未解決のレビュースレッドが無くなるまで4〜5を繰り返し、無くなったら終了する。
