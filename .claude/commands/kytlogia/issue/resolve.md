issue #$1 の対応を、役割の異なる2つのセッションで自動化する。

**レビューセッションは作業セッションと同時には起動しない。作業セッションがPRを作成した後に初めて起動する。** レビューすべきPRがまだ存在しない状態でレビューセッションを起動し、出現を最大30分ポーリングで待たせるのは無駄が大きいため。

**レビューセッションによる実際のレビュー(コードの読み込み・コメント投稿)は、Copilotレビューのラウンドが完了(または後述の理由でスキップ)してから開始する。** Copilotレビューの指摘は作業セッションがすぐに修正・pushするため、それと同時並行でレビューセッションがレビューを始めると、Copilotと同じ指摘が重複したり、修正で消えることが確定している行にコメントが付いたりして無駄が大きい。

**作業セッションとレビューセッションは互いに直接`SendMessage`を送り合えない。** 実地テストで、Agentツールで起動したサブエージェントには`ListAgents`が使えず、もう一方のセッションを名前で指定して`SendMessage`しても届かないことが判明した(`No agent named '...' is reachable.`)。確実に機能するのは、サブエージェントから自分を起動した親セッションへの`SendMessage(to: "main")`のみ。そのため、このコマンドを実行している親セッション自身が、両セッションの間の通知を中継するハブとして動作する設計にする(詳細は「フェーズ2」)。GitHubのPR状態(CIステータス・レビューコメント・レビュースレッドの解決状況)を正とする点は変わらず、中継が機能しない場合に備え各待機箇所にはポーリングをタイムアウト付きフォールバックとして残す。

## 起動前チェック

- `claude --version` がセッション間メッセージングに対応したバージョン(v2.1.224以降、Windowsはv2.1.234以降)か確認する。対応していない場合、このコマンドは`SendMessage`前提で設計しており対応バージョンでの実行が必須である旨をユーザーに報告し、ここで終了する。
- `gh issue view $1` でissueが存在しクローズされていないことを確認する。存在しない/クローズ済みならユーザーに報告してここで終了する。
- 作業セッション・レビューセッションはどちらも`Agent`ツールに `isolation: "worktree"` を指定して起動する。このコマンドを実行している親セッション自身のgitチェックアウト状態(ブランチ)が作業対象と異なる場合、隔離しないと作業セッションの`git checkout -b`等がその状態を引き継いでしまうため。

## セッションIDとコメントの付記

- 自分自身(このコマンドを実行しているセッション)のスクラッチパスなど環境情報に含まれるセッションUUIDの先頭8桁を`token`とする。取得できない場合は `uuidgen | cut -c1-8` などで代わりに生成する。
- 作業セッションのラベルは `$1-work-<token>`、レビューセッションのラベルは `$1-review-<token>` とする(Agent起動時のdescriptionにもこれを使う)。ただし前述の通りこれらは`SendMessage`の宛先としては使えない(あくまでフッターや報告上の識別用のラベル)。実際の宛先は、親セッションが`Agent`ツール起動時に得られる実際のagentId、またはサブエージェント側からは常に`"main"`を使う。
- 作業セッション・レビューセッションはそれぞれ起動後、自分自身(そのセッション)のスクラッチパスなど環境情報に含まれる**自分自身の**セッションUUIDの先頭8桁を`own_id`として把握する(取得できない場合は`uuidgen | cut -c1-8`)。`token`は親セッションのID、`own_id`はそのセッション自身のIDであり、両者は別物である。
- 各セッションがPRに投稿するコメント(レビューコメント・返信など)、および作業セッションが作成するPR本文には、末尾に`---`区切りを挟んで必ず以下の形式のフッターを付ける(イタリック等の装飾はしない、プレーンテキスト)。誰が/どのセッションが投稿・作成したかを区別できるようにするため。
  ```
  ---
  session: $1-work-<token>, session id: <own_id>
  ```
  レビューセッションの場合は1行目を `session: $1-review-<token>, session id: <own_id>` とする。
- レビュースレッドをresolveするだけの操作(新規コメントを伴わない)にはフッターは不要。

## フェーズ1: 作業セッションの起動

`Agent`ツールで作業セッション(description: `$1-work-<token>`、`isolation: "worktree"`)を`run_in_background: true`で起動し、返ってきたagentIdを`work_id`として控える。`send_later`等のセルフチェックインの仕組みが利用可能な環境では、起動と同時に30分後の自己確認を必ずスケジュールする(発火時の挙動は後述「通知が機能しない場合のフォールバック」を参照。SendMessage通知が届いていれば何もしない)。起動後はユーザーに「作業セッションを起動した。PR作成を待つ」旨を報告してターンを終える。以降は能動的なポーリングはせず、(a)作業セッションからの`SendMessage`通知(`to: "main"`)、(b)スケジュール済みの自己確認、(c)ユーザーからの状況確認、のいずれかをきっかけにフェーズ2へ進む(いずれの経路でも、フェーズ2に進む前提はPRが実際に作成されていることの確認である)。

以下をそのままAgentへのプロンプトとして渡す:

> issue #$1 に対応する。
>
> 0. 自分自身(このセッション)のスクラッチパスなど環境情報に含まれるセッションUUIDの先頭8桁を`own_id`とする。取得できない場合は`uuidgen | cut -c1-8`で代わりに生成する。以降のフッターに書く`<own_id>`はこの値のこと。**自分を起動した親セッション以外へ`SendMessage`することはできない(`ListAgents`も使えない)。他のセッションへの連絡は、以下の手順で指示された通り常に`to: "main"`で親セッションへ送ること。親セッションが中継する。**
> 1. `gh issue view $1` の内容を確認し、実装する。作業ブランチを切り、実装し、コミットする。
> 2. `gh pr create` でPRを作成する。本文に `Closes #$1` を含め、issueとリンクさせる。PR本文の末尾には`---`区切りを挟んで `session: $1-work-<token>, session id: <own_id>` というフッターを付ける。**PR作成が完了したら、次のステップに進む前に必ず`SendMessage`ツールで`to: "main"`宛にPR番号とURLを通知すること**(例:「PR #45 (https://github.com/.../pull/45) を作成した」)。この通知が届かないと親セッションはレビューセッションを起動できないため、他の作業より優先して送る。
> 3. `gh pr checks <PR番号> --watch` でCIの完了を待つ。ネットワーク到達性の問題などコードと明らかに無関係な原因で失敗した場合は再実行してよいが、**同一原因での再実行が3回目でも解消しない場合はそれ以上粘らない**。CIが完了しないままである旨と原因の見立てを`SendMessage`で`to: "main"`宛に報告し、セッションを終了する(以降の手順には進まない)。
> 4. (初回のみ)Copilotレビューの完了を待つ: `gh pr view <PR番号> --json reviews` などで `copilot-pull-request-reviewer` からのレビューが付くか、最大15分ポーリングする。レビューが付いたら、その内容がquota制限・レート制限によるエラー通知("quota"「レート制限」「unable to review」など、実質的な指摘を含まないエラーメッセージ)でないか確認する。エラー通知だった場合、実際のレビューは行われなかったものとして扱い(内容への対応は不要)、待たずに次に進む。15分経っても何も付かない場合も同様にquota制限でスキップされたとみなし、次に進む。
> 5. CIの失敗や(エラー通知でない)Copilotレビューの指摘があれば内容を確認して修正・pushする。インラインレビューコメントに対応した場合は、対応内容を1行で要約したフッター付き返信を該当スレッドに投稿する(`gh api repos/{owner}/{repo}/pulls/{pull_number}/comments/{comment_id}/replies`。`{pull_number}`は省略不可)。修正後は3(CIの完了待ち)だけをやり直す。4(Copilotレビュー待ち)は初回のみで、以降のpushのたびに繰り返さない(pushごとに再レビューされるとは限らず、毎回15分待つと大幅に遅延するため)。指摘が無くなるまでこれを繰り返す。
> 6. 4・5が完了(Copilotの初回ラウンドが終了、エラーでスキップ、またはタイムアウトでスキップ)したら、`SendMessage`で`to: "main"`宛に「Copilotラウンド完了、レビューを開始してよい」旨を通知する(親セッションがレビューセッションへ中継する)。
> 7. 親セッション経由で中継される、レビューセッションからの通知を待つ。**通知が主手段であり、能動的なポーリングはしない。** 通知の内容が「レビュー指摘あり」であれば8へ進む。「レビュー完了」であれば9へ進む。ただし通知が10分経っても届かない場合に限り、フォールバックとしてPRのレビュースレッド(`gh api graphql`などでレビューコメント一覧を取得)を1回だけ確認し、自分自身が5・8で付けたフッター(`$1-work-<token>`)を含まない未解決コメントがあれば8へ、無ければ9へ進む(自分の返信を指摘と誤認して無限ループするのを防ぐため)。判断がつかなければ再度通知待ちに戻る。
> 8. レビュー指摘の内容を確認して修正・pushする。対応内容を要約したフッター付き返信を該当スレッドに投稿する。**push後は`SendMessage`で`to: "main"`宛に「修正をpushした」旨を通知する。** その後7に戻り、レビューセッションからの次の通知(「レビュー指摘あり」または「レビュー完了」)を待つ。
> 9. CIがグリーンで未解決のレビュースレッドも無い状態になったら、その旨を`SendMessage`で`to: "main"`宛に最終報告してセッションを終了する(マージは行わない)。このセッションはここで完了するため、後でユーザーが「マージして」と言った場合はユーザー自身か、この作業セッションを起動した親セッションが直接`gh pr merge`を実行すること。

## フェーズ2: レビューセッションの起動と、以降の中継

作業セッションから`SendMessage`でPR番号・URLの通知を受け取ったら(この通知の送信元agentIdは`work_id`と一致するはずである)、その内容をそのままプロンプトに埋め込んで`Agent`ツールでレビューセッション(description: `$1-review-<token>`、`isolation: "worktree"`)を`run_in_background: true`で起動し、返ってきたagentIdを`review_id`として控える。レビューセッションはPRの存在をすでに知った状態で始まるため、PRを検索・ポーリングする必要が無い。起動後はユーザーに「PR #<PR番号> の作成を確認し、レビューセッションを起動した」旨を報告してターンを終える。

**この時点から、このコマンドの実行を終えるまで、親セッションは作業セッションとレビューセッションの間の通知を中継するハブとして動作する。** `work_id`または`review_id`からメッセージを受け取るたびに、以下の対応表に従ってもう一方へ`SendMessage`で転送し(内容は原則そのまま転送すればよい)、ターンを終えて次の通知を待つ、を繰り返す。

| 送信元                          | 内容                                             | 中継先                                                                                                                                                                                       |
| ------------------------------- | ------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 作業セッション(`work_id`)       | Copilotラウンド完了、レビューを開始してよい      | レビューセッション(`review_id`)                                                                                                                                                              |
| レビューセッション(`review_id`) | レビュー指摘あり                                 | 作業セッション(`work_id`)                                                                                                                                                                    |
| 作業セッション(`work_id`)       | 修正をpushした                                   | レビューセッション(`review_id`)                                                                                                                                                              |
| レビューセッション(`review_id`) | レビュー完了(指摘なし、または全て解消)           | 作業セッション(`work_id`)。これを受けた作業セッションは手順9(最終報告)へ進む。レビューセッションはこの通知の送信と同時に終了するため、以降このセッションからの追加中継は発生しない           |
| どちらか                        | CIが解消しない等の理由でセッションを終了する報告 | もう一方がまだ動いていれば、まず「相方のセッションが終了したため、あなたも今の作業を切り上げて終了してよい」という趣旨のメッセージを送ってから、ユーザーへ報告し、このコマンドの実行を終える |
| 作業セッション(`work_id`)       | 最終完了報告(手順9)                              | 中継不要。ユーザーへ報告し、このコマンドの実行を終える                                                                                                                                       |

以下のプロンプトの `<PR番号>` を通知されたPR番号に置き換えてAgentへ渡す:

> issue #$1 に対応するPR #<PR番号> をレビューする(このPRはすでに作成済みであることを作業セッションから通知されている)。
>
> 0. 自分自身(このセッション)のスクラッチパスなど環境情報に含まれるセッションUUIDの先頭8桁を`own_id`とする。取得できない場合は`uuidgen | cut -c1-8`で代わりに生成する。以降のフッターに書く`<own_id>`はこの値のこと。**自分を起動した親セッション以外へ`SendMessage`することはできない(`ListAgents`も使えない)。他のセッションへの連絡は、以下の手順で指示された通り常に`to: "main"`で親セッションへ送ること。親セッションが中継する。**
> 1. 親セッション経由で中継される、作業セッションからの「Copilotラウンド完了、レビューを開始してよい」という通知を待つ。**この通知が実際にレビューを開始してよい合図であり、主手段。能動的なポーリングはしない。** フォールバックの基準時刻は「レビューセッションが起動した時刻」ではなく「CIが最後にグリーンになった時刻」とする(作業セッション側のCopilot待ち上限と同じ基準に揃えないと、CIがすぐグリーンになった場合にCopilotの15分待ちの最中にフォールバックが先に成立してしまうため)。具体的には、`gh pr checks <PR番号>` でCIがグリーンであり、かつその状態になってから15分以上経過していて、その間新規コミットが無い場合に限り、通知が届いていなくてもレビューを開始してよい合図とみなす(CIがまだグリーンでない、またはグリーンになってから15分未満の間は、この条件は成立しないため通知を待ち続ける)。
> 2. 通知(またはフォールバック確認)を受けたら、念のためCIが依然グリーンであることを確認する(グリーンでなくなっていれば、再度手順1の通知待ちに戻る)。
> 3. `code-review` スキルでこのPRをレビューし、指摘があればインラインコメントとして投稿する(例: `/code-review <PR番号> --comment`)。各コメント本文の末尾にフッターを付ける。**コメント投稿が終わったら`SendMessage`で`to: "main"`宛に、1件以上コメントした場合は「レビュー指摘あり」、指摘が無かった場合は「レビュー完了」と通知する(親セッションが作業セッションへ中継する)。**「レビュー完了」を通知した場合はここでセッションを終了する。「レビュー指摘あり」を通知した場合は4へ進む。
> 4. 親セッション経由で中継される、作業セッションからの「修正をpushした」という通知を待つ。**通知が主手段であり、能動的なポーリングはしない。** ただし通知が10分経っても届かない場合に限り、フォールバックとして`gh pr view <PR番号> --json commits` で新規コミットの有無を1回だけ確認する。新規コミットが無ければ再度通知待ちに戻る。
> 5. 通知(またはフォールバック確認)で新規コミットを検知したら該当箇所を確認する。修正が妥当なら、そのレビュースレッドを解決する(`gh api graphql` の `resolveReviewThread` mutationを使う。新規コメントや返信は不要)。**他に未解決のレビュースレッドが無くなったら`SendMessage`で`to: "main"`宛に「レビュー完了」と通知してセッションを終了する。** まだ問題があれば追加でコメントし、`SendMessage`で`to: "main"`宛に「レビュー指摘あり」と通知する(親セッションが作業セッションへ中継する)。
> 6. 「レビュー完了」を通知するまで4〜5を繰り返す。

## 通知が機能しない場合のフォールバック

作業セッションがフェーズ1の手順2で`SendMessage`を送ったにもかかわらず、バックグラウンドセッションがターンを終えてしまう等の理由で親セッションのターンが再開せず、レビューセッションが起動しないことがありうる。同様に、フェーズ2開始後も親セッションが中継役として機能しないと、両セッションの間の連携全体が止まってしまう。これに備え、以下の2つのフォールバック経路を両方とも用意する。

- **ユーザー起点(常に有効)**: ユーザーから状況確認など何らかの働きかけがあった際、レビューセッションがまだ起動していなければ、作業セッションがすでにPRを作成済みでないかを`gh pr list --search "\"Closes #$1\" in:body"`で確認し、該当すればその場でフェーズ2を実行する。レビューセッションが既に起動している場合は、PRの現在の状態(CI・レビュースレッドの解決状況)を確認し、中継が滞っていないか(例えば片方が通知を送ったのにもう片方に転送されていない)を疑って必要なら手動で中継する。
- **自己起点(`send_later`等のセルフチェックインの仕組みが利用可能な環境のみ)**: 以下の2つの自己確認は別物であり、前者が役目を終えたら後者に切り替わる(両方同時に動かす必要はない)。`send_later`等の仕組みが利用できない環境では、両方省略しユーザー起点のフォールバックのみに頼る。
  - フェーズ1完了直後〜フェーズ2開始まで: 作業セッションを起動したら、必ず30分後に一度、PR作成有無を確認する自己確認をスケジュールする。発火時にレビューセッションが未起動であれば、上記と同じ方法でPR作成有無を確認する。PRが見つかればその場でフェーズ2を実行する(このための自己確認は以降不要になる。ただし下記のフェーズ2用の自己確認は別途スケジュールする)。まだ見つからなければ、さらに30分後にこの確認を再スケジュールする(作業セッション起動から合計3時間経ってもPRが見つからない場合は再スケジュールを打ち切り、ユーザーに状況を報告する)。
  - フェーズ2開始後(中継フェーズ): 作業セッションの最終完了報告(手順9)を受け取るまで、1時間おきに自己確認をスケジュールする。発火時にPRの状態(CI・レビュースレッドの解決状況)を確認し、両セッションの状態と食い違っていれば(例えば一方が既に反応しているのにもう一方に中継されていない)中継が滞っている可能性を疑い、必要なら手動で中継する。最終完了報告を受け取ったら、この自己確認のスケジュールも打ち切る。
