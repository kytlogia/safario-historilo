issue #$1 の対応を、役割の異なる2つのセッションで自動化する。

**レビューセッションは作業セッションと同時には起動しない。作業セッションがPRを作成した後に初めて起動する。** レビューすべきPRがまだ存在しない状態でレビューセッションを起動し、出現を最大30分ポーリングで待たせるのは無駄が大きいため。

セッション間の連携は`SendMessage`(`ListAgents`で発見できる、安定版・Claude Code v2.1.224以降/Windowsはv2.1.234以降の機能)による直接通知を主手段とする。ただしGitHubのPR状態(CIステータス・レビューコメント・レビュースレッドの解決状況)を正とする点は変わらない。`SendMessage`には既読確認や配送保証が無く、バックグラウンドセッションがターンを終えて通知を取りこぼす実運用上の懸念もあるため、各待機箇所にはポーリングをタイムアウト付きフォールバックとして残す。

## 起動前チェック

- `claude --version` がセッション間メッセージングに対応したバージョンか確認する。対応していない場合はユーザーに報告し、通知に頼らずポーリングのみで進めてよいか確認する。
- `gh issue view $1` でissueが存在しクローズされていないことを確認する。存在しない/クローズ済みならユーザーに報告してここで終了する。

## セッションIDとコメントの付記

- 自分自身(このコマンドを実行しているセッション)のスクラッチパスなど環境情報に含まれるセッションUUIDの先頭8桁を`token`とする。取得できない場合は `uuidgen | cut -c1-8` などで代わりに生成する。
- 作業セッションのIDは `$1-work-<token>`、レビューセッションのIDは `$1-review-<token>` とする(Agent起動時のdescriptionにもこれを使う)。`SendMessage`の宛先指定にもそのまま使う。
- 各セッションがPRに投稿するコメント(レビューコメント・返信など)には、末尾に必ず以下の形式でフッターを付ける。誰が/どのセッションが投稿したかをレビュアーが区別できるようにするため。
  - 作業セッション: ``_🤖 [Claude Code](https://claude.com/claude-code) · /kytlogia:issue:resolve 作業セッション (`$1-work-<token>`)_``
  - レビューセッション: ``_🤖 [Claude Code](https://claude.com/claude-code) · /kytlogia:issue:resolve レビューセッション (`$1-review-<token>`)_``
- レビュースレッドをresolveするだけの操作(新規コメントを伴わない)にはフッターは不要。

## フェーズ1: 作業セッションの起動

`Agent`ツールで作業セッション(description: `$1-work-<token>`)を`run_in_background: true`で起動する。起動後はユーザーに「作業セッションを起動した。PR作成を待つ」旨を報告してターンを終える。以降はポーリングせず、作業セッションからの`SendMessage`通知(`to: "main"`)を受け取ったらフェーズ2に進む。

以下をそのままAgentへのプロンプトとして渡す:

> issue #$1 に対応する。
>
> 1. `gh issue view $1` の内容を確認し、実装する。作業ブランチを切り、実装し、コミットする。
> 2. `gh pr create` でPRを作成する。本文に `Closes #$1` を含め、issueとリンクさせる。**PR作成が完了したら、次のステップに進む前に必ず`SendMessage`ツールで`to: "main"`宛にPR番号とURLを通知すること**(例:「PR #45 (https://github.com/.../pull/45) を作成した」)。この通知が届かないと親セッションはレビューセッションを起動できないため、他の作業より優先して送る。
> 3. `gh pr checks <PR番号> --watch` でCIの完了を待つ。
> 4. (初回のみ)Copilotレビューの完了を待つ: `gh pr view <PR番号> --json reviews` などで `copilot-pull-request-reviewer` からのレビューが付くか、最大15分ポーリングする。15分経ってもレビューが付かない場合はquota制限でスキップされたとみなし、次に進む。
> 5. CIの失敗やCopilotレビューの指摘があれば内容を確認して修正・pushする。インラインレビューコメントに対応した場合は、対応内容を1行で要約したフッター付き返信を該当スレッドに投稿する(`gh api repos/{owner}/{repo}/pulls/{pull_number}/comments/{comment_id}/replies`。`{pull_number}`は省略不可)。修正後は3(CIの完了待ち)だけをやり直す。4(Copilotレビュー待ち)は初回のみで、以降のpushのたびに繰り返さない(pushごとに再レビューされるとは限らず、毎回15分待つと大幅に遅延するため)。指摘が無くなるまでこれを繰り返す。
> 6. ここまでの指摘が解消したら、レビューセッション(`$1-review-<token>`、`ListAgents`で発見できる)からの「レビューコメントを投稿した」という`SendMessage`通知を待つ。**通知が主手段であり、能動的なポーリングはしない。** ただし通知が10分経っても届かない場合に限り、フォールバックとしてPRのレビュースレッド(`gh api graphql`などでレビューコメント一覧を取得)を1回だけ確認し、新規コメントがあれば7に進む。無ければ再度通知待ちに戻る。自分自身が5・7で付けたフッター(`$1-work-<token>`)を含むコメントは新規指摘としてカウントしない(自分の返信を指摘と誤認して無限ループするのを防ぐため)。
> 7. レビュー指摘が付いたら内容を確認して修正・pushする。対応内容を要約したフッター付き返信を該当スレッドに投稿する。**push後は`SendMessage`でレビューセッション(`$1-review-<token>`)へ「修正をpushした」旨を通知する。** 未解決のレビュースレッドが無くなるまで6〜7を繰り返す。
> 8. CIがグリーンで未解決のレビュースレッドも無い状態になったら、その旨をユーザーへの最終報告にまとめてセッションを終了する(マージは行わない)。このセッションはここで完了するため、後でユーザーが「マージして」と言った場合はユーザー自身か、この作業セッションを起動した親セッションが直接`gh pr merge`を実行すること。

## フェーズ2: PR作成通知を受けてレビューセッションを起動

作業セッションから`SendMessage`でPR番号・URLの通知を受け取ったら、その内容をそのままプロンプトに埋め込んで`Agent`ツールでレビューセッション(description: `$1-review-<token>`)を`run_in_background: true`で起動する。レビューセッションはPRの存在をすでに知った状態で始まるため、PRを検索・ポーリングする必要が無い。起動後はユーザーに「PR #<PR番号> の作成を確認し、レビューセッションを起動した」旨を報告してターンを終える。

以下のプロンプトの `<PR番号>` を通知されたPR番号に置き換えてAgentへ渡す:

> issue #$1 に対応するPR #<PR番号> をレビューする(このPRはすでに作成済みであることを作業セッションから通知されている)。
>
> 1. CIがグリーンになり(`gh pr checks <PR番号>`)、かつ直近数分間新規コミットが無い(CI修正やCopilotレビュー対応が落ち着いた)状態になるまで待つ。
> 2. `code-review` スキルでこのPRをレビューし、指摘があればインラインコメントとして投稿する(例: `/code-review <PR番号> --comment`)。各コメント本文の末尾にフッターを付ける。**コメント投稿(指摘なしの場合も)が終わったら`SendMessage`で作業セッション(`$1-work-<token>`、`ListAgents`で発見できる)へ「レビューコメントを投稿した」旨を通知する。**
> 3. 未解決の指摘がある場合、作業セッションからの「修正をpushした」という`SendMessage`通知を待つ。**通知が主手段であり、能動的なポーリングはしない。** ただし通知が10分経っても届かない場合に限り、フォールバックとして`gh pr view <PR番号> --json commits` で新規コミットの有無を1回だけ確認する。新規コミットが無ければ再度通知待ちに戻る。
> 4. 通知(またはフォールバック確認)で新規コミットを検知したら該当箇所を確認する。修正が妥当なら、そのレビュースレッドを解決する(`gh api graphql` の `resolveReviewThread` mutationを使う。新規コメントや返信は不要)。まだ問題があれば追加でコメントし、対応してもらうため作業セッションへ`SendMessage`で通知する。
> 5. 未解決のレビュースレッドが無くなるまで3〜4を繰り返し、無くなったら終了する。

## 通知が機能しない場合のフォールバック

- 作業セッションがフェーズ1の手順2で`SendMessage`を送ったにもかかわらず、バックグラウンドセッションがターンを終えてしまう等の理由で親セッションのターンが再開せず、レビューセッションが起動しないことがありうる。ユーザーから状況確認など何らかの働きかけがあった際は、レビューセッションがまだ起動しておらず作業セッションがすでにPRを作成済みでないかを`gh pr list --search "\"Closes #$1\" in:body"`で確認し、該当すればその場でフェーズ2を実行する。
- `send_later`などセルフチェックインの仕組みが利用可能な環境では、フェーズ1の作業セッション起動から30分後に一度だけ自己確認(レビューセッションが未起動なら上記と同じ方法でPR作成有無を確認し、あれば起動する)をスケジュールしてもよい。利用できない環境では、上記のユーザー起点のフォールバックのみに頼る。
