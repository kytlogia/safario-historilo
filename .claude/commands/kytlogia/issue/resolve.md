issue #$1 の対応を、役割の異なる2つのセッションで自動化する。

**レビューセッションは作業セッションと同時には起動しない。作業セッションがPRを作成した後に初めて起動する。** レビューすべきPRがまだ存在しない状態でレビューセッションを起動し、出現を最大30分ポーリングで待たせるのは無駄が大きいため。

**レビューセッションによる実際のレビュー(コードの読み込み・コメント投稿)は、Copilotレビューのラウンドが完了(または後述の理由でスキップ)してから開始する。** Copilotレビューの指摘は作業セッションがすぐに修正・pushするため、それと同時並行でレビューセッションがレビューを始めると、Copilotと同じ指摘が重複したり、修正で消えることが確定している行にコメントが付いたりして無駄が大きい。CIが一時的にグリーン+無変更に見える瞬間だけを条件にすると、Copilotの最大15分の待ち時間中に見切り発車してしまう恐れがあるため、CI状態のポーリングではなく作業セッションからの明示的な`SendMessage`通知を主な合図とする(詳細はフェーズ1手順6、フェーズ2手順1)。

セッション間の連携は`SendMessage`(`ListAgents`で発見できる、安定版・Claude Code v2.1.224以降/Windowsはv2.1.234以降の機能)による直接通知を主手段とする。ただしGitHubのPR状態(CIステータス・レビューコメント・レビュースレッドの解決状況)を正とする点は変わらない。`SendMessage`には既読確認や配送保証が無く、バックグラウンドセッションがターンを終えて通知を取りこぼす実運用上の懸念もあるため、各待機箇所にはポーリングをタイムアウト付きフォールバックとして残す。

## 起動前チェック

- `claude --version` がセッション間メッセージングに対応したバージョン(v2.1.224以降、Windowsはv2.1.234以降)か確認する。対応していない場合、このコマンドはフェーズ1・2間の連携を`SendMessage`前提で設計しており対応バージョンでの実行が必須である旨をユーザーに報告し、ここで終了する(ポーリングのみの代替フローはこのコマンドでは提供しない)。
- `gh issue view $1` でissueが存在しクローズされていないことを確認する。存在しない/クローズ済みならユーザーに報告してここで終了する。

## セッションIDとコメントの付記

- 自分自身(このコマンドを実行しているセッション)のスクラッチパスなど環境情報に含まれるセッションUUIDの先頭8桁を`token`とする。取得できない場合は `uuidgen | cut -c1-8` などで代わりに生成する。
- 作業セッションのIDは `$1-work-<token>`、レビューセッションのIDは `$1-review-<token>` とする(Agent起動時のdescriptionにもこれを使う)。`SendMessage`の宛先指定にもそのまま使う。
- 作業セッション・レビューセッションはそれぞれ起動後、自分自身(そのセッション)のスクラッチパスなど環境情報に含まれる**自分自身の**セッションUUIDの先頭8桁を`own_id`として把握する(取得できない場合は`uuidgen | cut -c1-8`)。`token`は親セッション(このコマンドの実行元)のID、`own_id`はそのセッション自身のIDであり、両者は別物である。
- 各セッションがPRに投稿するコメント(レビューコメント・返信など)、および作業セッションが作成するPR本文には、末尾に`---`区切りを挟んで必ず以下の形式のフッターを付ける(イタリック等の装飾はしない、プレーンテキスト)。誰が/どのセッションが投稿・作成したかを区別できるようにするため。
  ```
  ---
  session: $1-work-<token>, session id: <own_id>
  ```
  レビューセッションの場合は1行目を `session: $1-review-<token>, session id: <own_id>` とする。
- レビュースレッドをresolveするだけの操作(新規コメントを伴わない)にはフッターは不要。

## フェーズ1: 作業セッションの起動

`Agent`ツールで作業セッション(description: `$1-work-<token>`)を`run_in_background: true`で起動する。`send_later`等のセルフチェックインの仕組みが利用可能な環境では、起動と同時に30分後の自己確認を必ずスケジュールする(発火時の挙動は後述「通知が機能しない場合のフォールバック」を参照。SendMessage通知が届いていれば何もしない)。起動後はユーザーに「作業セッションを起動した。PR作成を待つ」旨を報告してターンを終える。以降は能動的なポーリングはせず、(a)作業セッションからの`SendMessage`通知(`to: "main"`)、(b)スケジュール済みの自己確認、(c)ユーザーからの状況確認、のいずれかをきっかけにフェーズ2へ進む(いずれの経路でも、フェーズ2に進む前提はPRが実際に作成されていることの確認である)。

以下をそのままAgentへのプロンプトとして渡す:

> issue #$1 に対応する。
>
> 0. 自分自身(このセッション)のスクラッチパスなど環境情報に含まれるセッションUUIDの先頭8桁を`own_id`とする。取得できない場合は`uuidgen | cut -c1-8`で代わりに生成する。以降のフッターに書く`<own_id>`はこの値のこと。
> 1. `gh issue view $1` の内容を確認し、実装する。作業ブランチを切り、実装し、コミットする。
> 2. `gh pr create` でPRを作成する。本文に `Closes #$1` を含め、issueとリンクさせる。PR本文の末尾には`---`区切りを挟んで `session: $1-work-<token>, session id: <own_id>` というフッターを付ける。**PR作成が完了したら、次のステップに進む前に必ず`SendMessage`ツールで`to: "main"`宛にPR番号とURLを通知すること**(例:「PR #45 (https://github.com/.../pull/45) を作成した」)。この通知が届かないと親セッションはレビューセッションを起動できないため、他の作業より優先して送る。
> 3. `gh pr checks <PR番号> --watch` でCIの完了を待つ。
> 4. (初回のみ)Copilotレビューの完了を待つ: `gh pr view <PR番号> --json reviews` などで `copilot-pull-request-reviewer` からのレビューが付くか、最大15分ポーリングする。レビューが付いたら、その内容がquota制限・レート制限によるエラー通知("quota"「レート制限」「unable to review」など、実質的な指摘を含まないエラーメッセージ)でないか確認する。エラー通知だった場合、実際のレビューは行われなかったものとして扱い(内容への対応は不要)、待たずに次に進む。15分経っても何も付かない場合も同様にquota制限でスキップされたとみなし、次に進む。
> 5. CIの失敗や(エラー通知でない)Copilotレビューの指摘があれば内容を確認して修正・pushする。インラインレビューコメントに対応した場合は、対応内容を1行で要約したフッター付き返信を該当スレッドに投稿する(`gh api repos/{owner}/{repo}/pulls/{pull_number}/comments/{comment_id}/replies`。`{pull_number}`は省略不可)。修正後は3(CIの完了待ち)だけをやり直す。4(Copilotレビュー待ち)は初回のみで、以降のpushのたびに繰り返さない(pushごとに再レビューされるとは限らず、毎回15分待つと大幅に遅延するため)。指摘が無くなるまでこれを繰り返す。
> 6. 4・5が完了(Copilotの初回ラウンドが終了、エラーでスキップ、またはタイムアウトでスキップ)したら、`SendMessage`でレビューセッション(`$1-review-<token>`)へ「Copilotラウンド完了、レビューを開始してよい」旨を通知する。レビューセッションがまだ起動しておらず`ListAgents`に見当たらない場合は、1分待って再試行し、最大10分試行する。10分経っても見当たらなければ諦めて次に進む(この通知が最終的に届かなくても、レビューセッション側にはCIグリーンから一定時間経過を条件とする独立のフォールバックがあるため、レビューが永久に始まらないことはない)。
> 7. ここまでの指摘が解消したら、レビューセッション(`$1-review-<token>`、`ListAgents`で発見できる)からの「レビューコメントを投稿した」という`SendMessage`通知を待つ。**通知が主手段であり、能動的なポーリングはしない。** ただし通知が10分経っても届かない場合に限り、フォールバックとしてPRのレビュースレッド(`gh api graphql`などでレビューコメント一覧を取得)を1回だけ確認し、新規コメントがあれば8に進む。無ければ再度通知待ちに戻る。自分自身が5・8で付けたフッター(`$1-work-<token>`)を含むコメントは新規指摘としてカウントしない(自分の返信を指摘と誤認して無限ループするのを防ぐため)。
> 8. レビュー指摘が付いたら内容を確認して修正・pushする。対応内容を要約したフッター付き返信を該当スレッドに投稿する。**push後は`SendMessage`でレビューセッション(`$1-review-<token>`)へ「修正をpushした」旨を通知する。** 未解決のレビュースレッドが無くなるまで7〜8を繰り返す。
> 9. CIがグリーンで未解決のレビュースレッドも無い状態になったら、その旨をユーザーへの最終報告にまとめてセッションを終了する(マージは行わない)。このセッションはここで完了するため、後でユーザーが「マージして」と言った場合はユーザー自身か、この作業セッションを起動した親セッションが直接`gh pr merge`を実行すること。

## フェーズ2: PR作成通知を受けてレビューセッションを起動

作業セッションから`SendMessage`でPR番号・URLの通知を受け取ったら、その内容をそのままプロンプトに埋め込んで`Agent`ツールでレビューセッション(description: `$1-review-<token>`)を`run_in_background: true`で起動する。レビューセッションはPRの存在をすでに知った状態で始まるため、PRを検索・ポーリングする必要が無い。起動後はユーザーに「PR #<PR番号> の作成を確認し、レビューセッションを起動した」旨を報告してターンを終える。

以下のプロンプトの `<PR番号>` を通知されたPR番号に置き換えてAgentへ渡す:

> issue #$1 に対応するPR #<PR番号> をレビューする(このPRはすでに作成済みであることを作業セッションから通知されている)。
>
> 0. 自分自身(このセッション)のスクラッチパスなど環境情報に含まれるセッションUUIDの先頭8桁を`own_id`とする。取得できない場合は`uuidgen | cut -c1-8`で代わりに生成する。以降のフッターに書く`<own_id>`はこの値のこと。
> 1. 作業セッション(`$1-work-<token>`、`ListAgents`で発見できる)からの「Copilotラウンド完了、レビューを開始してよい」という`SendMessage`通知を待つ。**この通知が実際にレビューを開始してよい合図であり、主手段。能動的なポーリングはしない。** フォールバックの基準時刻は「レビューセッションが起動した時刻」ではなく「CIが最後にグリーンになった時刻」とする(作業セッション側のCopilot待ち上限と同じ基準に揃えないと、CIがすぐグリーンになった場合にCopilotの15分待ちの最中にフォールバックが先に成立してしまうため)。具体的には、`gh pr checks <PR番号>` でCIがグリーンであり、かつその状態になってから15分以上経過していて、その間新規コミットが無い場合に限り、通知が届いていなくてもレビューを開始してよい合図とみなす(CIがまだグリーンでない、またはグリーンになってから15分未満の間は、この条件は成立しないため通知を待ち続ける)。
> 2. 通知(またはフォールバック確認)を受けたら、念のためCIが依然グリーンであることを確認する(グリーンでなくなっていれば、再度手順1の通知待ちに戻る)。
> 3. `code-review` スキルでこのPRをレビューし、指摘があればインラインコメントとして投稿する(例: `/code-review <PR番号> --comment`)。各コメント本文の末尾にフッターを付ける。**コメント投稿(指摘なしの場合も)が終わったら`SendMessage`で作業セッション(`$1-work-<token>`、`ListAgents`で発見できる)へ「レビューコメントを投稿した」旨を通知する。**
> 4. 未解決の指摘がある場合、作業セッションからの「修正をpushした」という`SendMessage`通知を待つ。**通知が主手段であり、能動的なポーリングはしない。** ただし通知が10分経っても届かない場合に限り、フォールバックとして`gh pr view <PR番号> --json commits` で新規コミットの有無を1回だけ確認する。新規コミットが無ければ再度通知待ちに戻る。
> 5. 通知(またはフォールバック確認)で新規コミットを検知したら該当箇所を確認する。修正が妥当なら、そのレビュースレッドを解決する(`gh api graphql` の `resolveReviewThread` mutationを使う。新規コメントや返信は不要)。まだ問題があれば追加でコメントし、対応してもらうため作業セッションへ`SendMessage`で通知する。
> 6. 未解決のレビュースレッドが無くなるまで4〜5を繰り返し、無くなったら終了する。

## 通知が機能しない場合のフォールバック

作業セッションがフェーズ1の手順2で`SendMessage`を送ったにもかかわらず、バックグラウンドセッションがターンを終えてしまう等の理由で親セッションのターンが再開せず、レビューセッションが起動しないことがありうる。これに備え、以下の2つのフォールバック経路を両方とも用意する。

- **ユーザー起点(常に有効)**: ユーザーから状況確認など何らかの働きかけがあった際、レビューセッションがまだ起動していなければ、作業セッションがすでにPRを作成済みでないかを`gh pr list --search "\"Closes #$1\" in:body"`で確認し、該当すればその場でフェーズ2を実行する。
- **自己起点(`send_later`等のセルフチェックインの仕組みが利用可能な環境のみ)**: フェーズ1で作業セッションを起動したら、必ず30分後に一度自己確認をスケジュールする。発火時にレビューセッションが未起動であれば、上記と同じ方法でPR作成有無を確認する。PRが見つかればその場でフェーズ2を実行し、以降の自己確認はスケジュールしない。まだ見つからなければ、さらに30分後の自己確認を再スケジュールする(作業セッション起動から合計3時間経ってもPRが見つからない場合は再スケジュールを打ち切り、ユーザーに状況を報告する)。`send_later`等の仕組みが利用できない環境では、この経路は省略しユーザー起点のフォールバックのみに頼る。
